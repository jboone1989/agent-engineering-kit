# Agent Engineering Kit 中文使用指南

这个开源工具包解决的是一个通用问题：**编码 Agent 容易只顾当前功能可运行，反复向现有模块添加逻辑，最终造成耦合和技术债。**

工具包并不替 Agent 设计架构，而是把团队确定的边界写进项目，并让每次提交自动检查。

## 安装工具包

在工具包源码目录：

```bash
python -m pip install -e .
```

用于现有 Python 项目（必须把包名和模块名改成项目中实际存在的名称）：

```bash
aegkit init /path/to/repo --language python --package mypackage \
  --forbid learning:publishing \
  --test "python -m pytest -q"
```

用于现有 TypeScript 项目：

```bash
aegkit init /path/to/repo --language typescript --source src \
  --forbid learning:publishing \
  --test "npm test"
```

在 Python 项目安装 `import-linter`；在 TS 项目将 `dependency-cruiser` 安装为开发依赖。项目自己的测试依赖仍应正常安装。生成的 CI 工作流可能需要补上原项目的安装步骤。

## 升级通用工具（不覆盖项目规则）

工具包升级后运行 `aegkit sync /path/to/repo`。它只会更新上次由工具包生成、此后没有被项目手动修改的 `guard.py` 和 CI 工作流。项目自己的 `policy.json` 不会被自动覆盖。

## 每次改代码都执行

```bash
python .agent-engineering/guard.py doctor
python .agent-engineering/guard.py check
```

`check` 会自动从 `.agent-engineering/policy.json` 生成底层检查配置，运行架构检查，然后运行配置里的功能测试。如果任一失败，返回非零退出码。`--arch-only` 仅用于定位问题，不应作为合并验收。

## 项目间复用方式

- 工具包集中维护**执行器和规则模板**。
- 每个项目各自维护**模块所有权、禁止依赖、功能测试命令**。
- Codex 读取 `AGENTS.md`，Claude Code 通过 `CLAUDE.md` 引用它。
- GitHub Actions 执行 `.agent-engineering/guard.py check`，不依赖工具包先上传 PyPI。
- 配置和 CI 都不要随功能代码由 Agent 自行降低要求；在 GitHub 设置必须通过的 CI 状态，以及配置文件人工审查。

## 已有技术债怎么办？

先为**已经清洁的边界**开启阻断规则；旧问题记录下来，逐步减少。不要为了让旧仓库立刻通过，而把所有违规都加进永久忽略列表。

## 目前边界

目前只自动支持 Python 和 TypeScript，Java 提供 ArchUnit 接入说明。它不能判断一个模块有没有好好承担单一职责，也不能检测所有运行时共享状态。检查通过 ≠ 整个架构良好；还需要模块测试与代码审查。

代码采用 MIT 许可证，可以被别的项目复用、修改和分发。目前提供的是可开源的源码包，**尚未实际公开发布到 GitHub 或 PyPI**。


## v0.3：严格模块白名单

可以在 `.agent-engineering/policy.json` 中配置 `modules` 列表和 `allowed_dependencies` 二元组。它们覆盖的所有模块之间，只有白名单中的依赖被允许；**未声明的模块不在白名单约束范围内**，请把真实模块补齐。旧版的 `forbidden` 配置仍然有效。

新的 `real-adapters` CI 测试真实安装 Python Import Linter 和 TypeScript dependency-cruiser，执行「通过→故意违规→修复通过」。没有安装这些工具时，CI 会明确失败，不会跳过然后显示绿色。

## v0.3.2：命令超时与真实适配器验收

`policy.json` 可配置 `"command_timeout_seconds": 900`（1–3600 秒），命令超时返回失败，避免工程检查卡住。`doctor` 不再只检测 `npx` 是否存在，还会实际检查 `depcruise`。

2026-10-09 已在隔离临时环境真实验证 Python Import Linter 与 TypeScript dependency-cruiser 对正常、非法依赖、修复后的代码的检测；但 GitHub Actions 端到端验收和公开仓库发布仍未完成。详细记录见 `verification-2026-10-09.md`。

## v0.4：strict 模式，policy 不再能被悄悄放宽

在 policy.json 中设 `"strict": true` 后：

- **policy 变更必须单独 PR**：CI 传入 base ref 后，改 policy.json 的提交不能同时改其他代码（白名单：`.agent-engineering/**`、`engineering-guard.yml`、`ARCHITECTURE.md`）。先落 policy，再在后续 PR 里用新自由度。
- **放宽必须留痕**：删 forbidden、删 allowed 边、删 modules 成员、关 coverage/cycles、删 tests、关 strict，都必须有带日期和理由的 `relaxations` 条目；条目用 SHA-256 链接，删改历史即断链，所有检查变红。
- **唯一放宽入口**：`aegkit relax <项目> --reason "理由" --remove-forbidden a:b`。理由为空、或请求根本不是放宽，命令直接拒绝。

strict 是可选项；不加字段的 policy 行为与 0.3.3 完全一致。它防的是"悄悄的侵蚀"，不防"商量好的侵蚀"——人审仍是最后一道闸。
